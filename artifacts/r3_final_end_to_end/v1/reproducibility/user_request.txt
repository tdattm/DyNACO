# 2. SCIENTIFIC HYPOTHESIS

## Main hypothesis

Adaptive allocation of a fixed number of additional local-search candidate slots can yield better TSP tours than:

1. Original fixed K32 local search.
2. Uniform fixed K40 local search with the same total number of candidate slots.

The comparison is under equal wall-clock search budgets.

## Why the K40 control is mandatory

Comparing Adaptive K32/K64 only against K32 is insufficient.

An improvement could arise merely because the adaptive method evaluates more candidate edges.

The K40 control tests whether **where we allocate the extra edges** matters beyond the simple act of adding the same number of candidate slots uniformly.

Use three arms:

### ARM A — ORIGINAL K32

- Exactly 32 nearest-neighbor candidates per node for native SRR.
- Original sampling graph K32.
- Original GNN input and checkpoint.
- Original pheromone semantics.
- Original ACO behavior.
- Exactly one original SRR call.
- No adaptive allocation.

Total directed SRR candidate slots:

`1000 × 32 = 32000`

### ARM B — UNIFORM K40

- Exactly 40 nearest-neighbor candidates per node for native SRR.
- Use ranks 1–40 from the native nearest-neighbor ordering.
- Original sampling graph remains K32.
- Original GNN input remains K32.
- Original pheromone dimensions remain K32.
- Exactly one SRR call.

Total directed SRR candidate slots:

`1000 × 40 = 40000`

### ARM C — ADAPTIVE K32/K64

- 750 nodes receive 32 native SRR candidates.
- 250 nodes receive 64 native SRR candidates.
- Nodes are selected using a deterministic state-dependent allocation score.
- Original sampling graph remains K32.
- Original GNN input remains K32.
- Original pheromone dimensions remain K32.
- Exactly one SRR call.

Total directed SRR candidate slots:

`750 × 32 + 250 × 64 = 40000`

Thus ARM B and ARM C have exactly the same directed-slot budget.

Also report unique undirected edge counts, but do not confuse them with directed candidate slots.

# 3. EXACT ADAPTIVE ALLOCATION POLICY

Use a deterministic geometry-and-tour-excess policy based on the original R3 Stage A selector idea.

Do not introduce a learned allocator, reinforcement learning, GNN retraining, oracle-guided allocation, or parameter search.

For each node u, from the currently available global-best tour at the beginning of an allocation epoch, compute:

- Its predecessor pred(u).
- Its successor succ(u).
- The Euclidean distance to its predecessor.
- The Euclidean distance to its successor.
- The mean Euclidean distance to its original K32 nearest neighbors.

Define:

`excess(u) = max(dist(u, pred(u)), dist(u, succ(u)))`

`local_scale(u) = max(mean_distance_to_K32_neighbors(u), 1e-12)`

`score(u) = excess(u) / local_scale(u)`

Sort nodes by descending score.

Break exact score ties by ascending node index.

Select exactly the top 250 nodes.

These nodes receive K64 SRR candidate access.

All other nodes receive K32 SRR candidate access.

Do not use the principal optimal tour, independently computed oracle moves, future trajectories or benchmark outcomes when selecting nodes.

### Update schedule

Recompute the allocation before iterations:

`0, 100, 200, 300, ...`

That means once every 100 ACO iterations.

Use the current native global-best tour available before the next iteration starts.

At iteration zero, use the initialized native global-best tour.

Do not alter the original solver's RNG state during allocation.

Do not select nodes using any information from a future iteration.

Use the same allocation schedule and deterministic computation for every principal run.

If there is any mismatch between the original Stage A geometry scoring implementation and this specification, document it before principal execution and treat the formulas above as authoritative for this NEW study.

Do not tune the policy based on principal results.
